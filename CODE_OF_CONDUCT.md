## Our Commitment

Tervynix aims to maintain a professional, respectful, and constructive environment for developers, contributors, users, maintainers, sponsors, and community members.

Everyone participating in the Tervynix community is expected to contribute to an environment that encourages technical discussion, learning, collaboration, and responsible software development.

This Code of Conduct applies to:

* GitHub Issues
* Pull Requests
* GitHub Discussions
* Code reviews
* Documentation contributions
* Community conversations
* Project-related communication
* Public collaboration spaces associated with Tervynix

---

## Expected Behavior

Community members are expected to:

* Communicate respectfully and professionally
* Give constructive technical feedback
* Respect different levels of experience and technical backgrounds
* Focus disagreements on ideas, implementations, and engineering decisions rather than individuals
* Provide useful context when reporting bugs or proposing changes
* Respect project maintainers and contributor time
* Accept constructive feedback
* Help maintain clear and productive technical discussions
* Follow security disclosure procedures
* Respect intellectual property and licensing requirements
* Avoid intentionally misleading claims about the project or its contributors

---

## Unacceptable Behavior

The following behavior is not acceptable:

* Harassment or intimidation
* Personal attacks
* Discriminatory or hateful language
* Threats or abusive communication
* Repeated disruption of technical discussions
* Deliberate misinformation
* Spam
* Unsolicited advertising
* Publishing another person's private information without permission
* Sharing credentials, secrets, tokens, or private project information
* Attempting to exploit security vulnerabilities against Tervynix users or infrastructure
* Submitting malicious code
* Intentionally introducing backdoors or destructive behavior
* Impersonating project maintainers or contributors
* Claiming unofficial forks or derivative projects are officially affiliated with Tervynix without authorization

---

## Technical Discussions

Engineering disagreements are normal and welcome when handled professionally.

When discussing architecture, implementation, APIs, runtime behavior, performance, security, or product direction:

1. Focus on technical evidence.
2. Explain tradeoffs clearly.
3. Provide reproduction steps when reporting failures.
4. Include relevant logs, tests, or examples where appropriate.
5. Avoid turning technical disagreement into personal criticism.
6. Respect final maintainer decisions even when alternative approaches exist.

The goal is to improve the project, not to win arguments.

---

## Bug Reports

When reporting a bug, contributors should provide enough information for maintainers to understand and reproduce the problem.

Useful information includes:

* Environment
* Operating system
* Runtime versions
* Relevant dependencies
* Steps to reproduce
* Expected behavior
* Actual behavior
* Relevant logs
* Screenshots where useful
* Minimal reproduction examples when possible

Do not include passwords, API keys, access tokens, private repository content, or other sensitive information.

---

## Security Vulnerabilities

Security vulnerabilities must not be publicly disclosed before maintainers have had a reasonable opportunity to investigate them.

Do not publish:

* Working exploits
* Private credentials
* Access tokens
* Infrastructure secrets
* Sensitive user information
* Detailed attack instructions against active Tervynix infrastructure

Follow the process described in [SECURITY.md](./SECURITY.md).

---

## Contributions

All contributions should:

* Be relevant to Tervynix
* Follow project contribution guidelines
* Avoid intentionally unnecessary dependencies
* Avoid malicious or hidden functionality
* Include appropriate tests where applicable
* Respect project architecture and security boundaries
* Follow repository licensing requirements

See [CONTRIBUTING.md](./CONTRIBUTING.md) for contribution guidance.

---

## Project Decisions

Tervynix maintainers are responsible for:

* Project architecture
* Security decisions
* Repository governance
* Release direction
* Contribution acceptance
* Public project representation
* Moderation decisions

Constructive proposals and alternative approaches are encouraged.

However, maintainers may decline changes that do not align with the project's architecture, roadmap, security requirements, reliability standards, or long-term direction.

---

## Enforcement

Project maintainers may take action when this Code of Conduct is violated.

Depending on the severity and context, actions may include:

* Requesting changes in communication or behavior
* Editing or removing inappropriate content
* Closing discussions
* Closing issues
* Rejecting contributions
* Removing comments
* Restricting participation
* Blocking users from project spaces

Serious security abuse, harassment, malicious contributions, or deliberate attacks may result in immediate restriction from the project.

---

## Reporting Problems

If you experience or observe behavior that violates this Code of Conduct, report it privately to the project maintainer where possible.

For security-related matters, follow [SECURITY.md](./SECURITY.md).

Reports should contain enough information to understand:

* What happened
* Where it happened
* When it happened
* Relevant links or evidence
* Any additional context

Reports will be reviewed as responsibly as possible.

---

## Scope

This Code of Conduct applies to official Tervynix project spaces and to individuals representing Tervynix in official project-related activities.

It does not control unrelated personal activity outside the project unless that activity directly involves impersonation, abuse, security threats, or misrepresentation of the Tervynix project.

---

## Community Goal

Tervynix is being built as a serious developer platform.

Its community should reflect the same standards:

**Professional communication.
Strong engineering.
Constructive collaboration.
Responsible security.
Respect for developers.**
